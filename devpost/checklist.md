## Revisions

- The default model for reading orders is `gemini-3.6-flash`, not `gemini-3.8-flash` — on the free tier (6 Nov), 3.8 answered "503 high demand" and then took over 30 s, while 3.6 read the sample chat correctly in about 5 s. Calls use thinking level LOW (MINIMAL for the intent check), because Gemini 3 models think by default and were slow. The model stays a setting (`GEMINI_READ_MODEL`).
- Tool versions: TypeScript 5.9 and ESLint 9, not the newest TypeScript 7 and ESLint 10 — the Next.js and typescript-eslint lint plugins don't support those yet. Node 23.7 (the learner's install) runs everything, including `better-sqlite3`, even though Vitest and ESLint list Node 23 as unsupported (it's past end-of-life); slice 8 pins Render to Node 22 LTS.
- PayPal's `invoice_id` will be the order number plus a short unique suffix (for example `1001-k3f9`), not the bare number — PayPal rejects a repeated invoice ID, and Reset demo restarts numbering at #1001.
- The PayPal sandbox shop and buyer must be **United States** accounts, with the app linked to the US business account. With an Egypt business account, PayPal approved the payment but refused the capture ("possible compliance violation"); the US pair captured and refunded $128.00 cleanly (7 Nov). The sandbox capture returned everything the spec reads: payer name and email, ship-to name and full address, and the fee and net (`seller_receivable_breakdown`: $4.96 fee, $123.04 net on $128.00). The Devpost testing instructions (`6-ship`) must give judges a US sandbox buyer.
- Step 2 small additions: the customer phone shows which made-up customer you are ("You're Maya Brooks") and reopens on the newest conversation after a refresh; on phone-width screens the guide line says "run the shop from the Seller phone" instead of "on the right". The database rebuilds itself when `schema.sql` changes version (demo data only), so later steps can add columns without a migration tool. `MessageChannel.send` takes the finished message; the demo channel saves it.
- The pay page uses **PayPal's JS SDK v6** (`@paypal/react-paypal-js/sdk-v6`: `PayPalProvider` and `PayPalOneTimePaymentButton`), not the v5 `PayPalScriptProvider` and `PayPalButtons` the spec named: version 10.6.1 of the package labels v5 "Legacy SDK" and no longer ships its docs. The flow is the same (our server creates the PayPal order from the frozen order and captures it after approval). Only the PayPal button is shown for now; Pay Later and card buttons are optional polish for step 7. v6 has no `actions.restart()`, so a declined payment shows "PayPal couldn't take this payment. Please try again." and the buyer taps the button again, which reuses the same PayPal order while it's still payable.
- Step 3 storage: the draft waiting in the reply box lives in its own `drafts` table (one per conversation) instead of draft columns on `orders`, and a sent payment message keeps its `pay_token` so the customer phone shows the "Pay with PayPal" card. Two small routes were added for filling the card by hand: `POST /api/conversations/[id]/order` (start an order) and `POST /api/orders/[id]/items` (add an item).
- Step 5 messages: the AI writes the questions and the payment message's opening line, while our code always inserts the order number, total and link; if the AI is down, a plain fixed sentence is used, so nothing blocks. The **thank-you and refund messages stay fixed text** (cut #3 from the approved cut list, applied early): it keeps "Paid" instant on the pay page and saves free-tier calls. Short writing uses `gemini-3.5-flash-lite` with minimal thinking (about 1 s); Read order uses `gemini-3.6-flash` (about 5 s live).
- Step 5 discovery: on "one white linen shirt", Gemini returned the quantity as the word "one", which the digits-only rule threw away. The quantity rule now reads "a", "one" … "twelve" and "2 dresses", and the AI schema asks for digits. "Read again" appears when the customer wrote after the last `OrderRead` timeline line, instead of storing a last-read message ID on the order. Schema version 3 adds `drafts.by_ai` (AI blue only for AI-written drafts), and the server re-checks the schema version when its code reloads, so a running dev server picks up schema changes without a restart.
- Step 6 agent: it asks the AI for the customer's intent only when that changes the proposal (an order awaiting payment or paid). While an order is being filled in, the order alone decides between Ask and Request payment, which saves free-tier calls. The once-per-message lock lives in the server process, which is fine for one Render instance. Approving Ask writes the question into the reply box, and approving Remind drafts a fixed-text nudge with the same pay link. An open proposal replaced by a newer customer message is removed, not marked dismissed, so the timeline shows only real decisions. Live: "is it still available? I'll pay tonight" on an unpaid order led to a Remind proposal in 2 s.
- Step 6 run, found by the learner: the sandbox buyer paid from its linked bank account, and PayPal's capture came back **PENDING (reason ECHECK)**, not COMPLETED. The app treated that as a mismatch, kept the order Awaiting payment, and let the pay page start a second payment (PayPal refused it: same invoice). Fixed: a PENDING capture of the right amount counts as **Paid**, marked "PayPal is still clearing it"; the pay page never starts a new PayPal payment once one was captured or while the shop is checking a flagged payment ("No need to pay again"). PayPal may refuse to refund a payment that is still clearing, so the Devpost testing instructions (`6-ship`) should tell judges to pay with the sandbox buyer's **card**, not the bank account.
- Step 6 rerun: the buyer again paid by bank (PENDING), and approving the agent's refund **cancelled** the still-clearing payment. PayPal now shows that capture as DECLINED and returned the capture's own ID as the "refund" ID; no money moved, and the app shows Refunded with a $0.00 balance. This is fine for the demo, but it confirms that judges should pay by card to see a normal completed capture and refund.
- Step 7 Orders tab: each row's date is when the order was first saved. The order itself has no date, so the order store returns it next to each order for this list. Tapping a row opens the chat with the order card already up, and the back button reads "‹ Orders". On a phone, the empty Inbox now says "Type as the customer on the Customer phone" instead of "on the left". The demo page's second note tells judges to log in as the sandbox buyer from the testing notes and pay with the saved card, because bank payments stay pending.
- Step 7 learner check: the learner tapped **+ Add item** by mistake and couldn't get rid of the blank item, which then blocked Request payment. Each item now has a **Remove** button while the order can still change. It asks first if the item already has values, refuses to remove the only item ("Cancel the order instead"), renumbers the items left, adds "Item 2 removed" to the timeline, and drops a question in the reply box that was about the removed item. This is narrower than the deferred "editing items": item values were already editable, and only removal is new.
