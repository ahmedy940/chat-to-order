Chat to Paid: technical spec

One Next.js app on Render's free tier. Gemini reads the chat and proposes; PayPal's REST APIs take and return the money; the seller approves every step.

Canonical file: devpost/spec.md

How the pieces fit

Dependencies point inward: routes → use cases → domain. Adapters plug into ports, wired in src/server/container.ts. Swapping Gemini for Claude or adding WhatsApp is one new adapter.

The payment round trip

Refund: seller approves → our server calls POST /v2/payments/captures/{id}/refund (empty body = full) with PayPal-Request-Id = refund-{orderId} → Refunded. No webhooks needed for this build.

Money safety rules

Amounts never come from the AI

The AI only proposes which action. Amounts come from the frozen order, in integer cents.

Check before Paid

Captured amount and currency must equal the frozen total. A mismatch stays Awaiting payment and is flagged.

No double charge or refund

Every PayPal write has a PayPal-Request-Id; Paid stays Paid; Refunded stays Refunded.

Seller approves every money action

NextActionPolicy only allows Refund on Paid orders and Request payment when nothing is missing.

Append-only timeline and ledger

Each state change writes one order_events row in the same transaction as the status. Money rows are signed cents (+capture, −refund). Tests: Paid ⇒ balance = total; Refunded ⇒ balance = 0.

Why statuses plus a log, not full event sourcing?

The status stays the source of truth for the rules, so nothing is rebuilt by replaying events (no projections or event versioning). PayPal is already the system of record for money. The log gives the audit trail (who approved what) and a balance that later makes partial refunds simple.

Why not the PayPal Agent Toolkit at runtime?

Its tools let the AI fill in amounts and parameters. We keep money out of the AI's hands. Its tool names also differ across versions (pay_order vs capture_order). A toolkit adapter can sit behind the same PaymentGateway port if time remains. Disclosed in the submission.

Failure modes
  • Gemini limited or invalid → "Couldn't read this conversation"; seller types details and can still request payment.
  • PayPal down → nothing changes; retries are safe.
  • Declined after approval → buyer retries through PayPal's buttons.
  • Amount mismatch → not Paid, flagged.
  • Paid twice in two tabs → second capture returns Paid.
  • PayPal order expired → a new one is created on the next attempt.
  • Render asleep or restarted → slow first load; data cleared; record the video locally.
How someone runs it
  • Hosted: the Render URL; sandbox buyer login in the Devpost testing notes, never in the repo.
  • Local: npm install → copy .env.example to .env.local (Gemini key, PayPal sandbox client ID and secret, public client ID, base URL) → npm run dev.
